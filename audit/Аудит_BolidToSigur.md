# Аудит BolidToSigur

Дата: 29.09.2026. Коммит: `2be85ab`. Проверка кода и синтетические тесты, без доступа к рабочей базе, Windows, контроллерам и установленному Sigur. Исходные программы не изменены, в GitHub ничего не отправлено.

## Вывод

Текущую цепочку нельзя считать готовой для массового переноса ключей. Есть подтверждённые потери данных и недостаточная проверка номеров. Конкретную причину сбоя на объекте нельзя установить без лога и схемы базы. Нельзя утверждать, что у «старых карт» отсутствует номер, лишь потому что используемый алгоритм не смог его разобрать.

## Критические и существенные находки

### 1. Восстановление .bak: режим транзакций и небезопасное имя базы

`ИНСТРУКЦИЯ/Выгрузка_из_резервной_копии.pyw:146–171, 482–540`.

`pyodbc.connect` вызывается без `autocommit=True` (по умолчанию autocommit отключён); отдельного переключения перед RESTORE нет. RESTORE DATABASE нельзя выполнять внутри явной/неявной транзакции. Это дефект подготовки подключения и вероятная причина отказа пути через .bak. Точный текст отказа нужно подтвердить логом SQL Server. Тест подтверждает параметры вызова, не исполнение RESTORE.

Используется постоянное имя `OrionCopyExport`: существующая база с этим именем удаляется без проверки происхождения. Ошибка DROP подавляется, затем выполняется RESTORE WITH REPLACE. Это не защита от удаления чужой базы с совпавшим именем. Пути MOVE берутся из резервной копии — на другом сервере таких каталогов может не быть. Путь .bak должен быть доступен службе SQL Server, а не только пользователю программы. Нет явного обработки всех результатов RESTORE через nextset перед закрытием подключения.

Исправление: отдельный тестовый SQL Server; отдельное административное подключение с autocommit; уникальное имя и файлы; отказ при существующей базе; без WITH REPLACE; каталоги целевого сервера; проверка завершения RESTORE и состояния ONLINE. Не ограничиваться одной правкой autocommit: она позволит исполниться и опасному удалению.

### 2. Номера ключей принимаются без достаточной валидации

`ИНСТРУКЦИЯ/Миграция_Болид_Sigur.pyw:324–402`.

Подтверждено вызовами реальной функции:
- `ABC` принимается как код с пометкой «непонятная длина (3)»;
- `123456789012345678` превращается в `12345678` простым отрезанием справа;
- `999,99999` принимается как W26, хотя значения выходят за диапазоны 8-битного facility code и 16-битного номера.

Непустой результат попадает в список карт и затем в файл, даже если объяснение содержит «СВЕРИТЬ» или «непонятная длина». HEX из одних цифр не отличают от десятичного представления. Формат источника должен задаваться явно. Нераспознанные, неподтверждённые и невалидные коды нужно помещать в отдельный реестр, а не допускать в импорт.

### 3. Правило W34 не совпадает с буквальным описанием

`ИНСТРУКЦИЯ/Миграция_Болид_Sigur.pyw:124–181`, README.

Написано «8 hex-знаков до 01 в конце», но код берёт `d[-11:-3]` — смещение на половину байта относительно `d[-10:-2]`. Для синтетического `1122334455667701` результат `34455667`, тогда как непосредственно перед `01` стоят `44556677`.

Это доказанное расхождение реализации с описанием, **не доказательство правильности альтернативного среза для настоящих карт**. В коде упоминается смещение Wiegand-потока; без реальных пар нельзя просто заменить индексы. Обработка FE01, обращение байтов и выбор длины 16 — эвристики без тестовых эталонов в репозитории.

`fit_card_rule:248–321` подбирает правило по одному совпадению среди всех карт и распространяет его на весь файл. Максимальное число формально обрабатываемых кодов не доказывает правильность. Нужны привязанные к конкретной записи пары исходный CodeP ↔ номер в Sigur, несколько примеров каждого семейства карт, контрольные примеры, нули и разные длины.

### 4. Тихая потеря шестого и последующих ключей

`ИНСТРУКЦИЯ/Миграция_Болид_Sigur.pyw:873`, `Конвертер_Орион_в_Sigur.py:237` — `codes[:5]`.

Тест: 7 исходных карт одного сотрудника, в записанном XLS только 5. В отчёте GUI число кодов считается до обрезания (`Миграция…:1138`), поэтому отчёт не отражает фактический результат.

Даже если конкретная версия/настройка Sigur ограничивает число пропусков, недопустима тихая потеря: нужен явный отказ или реестр исключений с выбором разрешённых карт. Ограничение целевой системы этим аудитом не проверено.

### 5. Предположения о схеме могут ломать SQL-выгрузку

`ИНСТРУКЦИЯ/Выгрузка_из_Болид.pyw:184–212, 292–398` и дублированный код выгрузки из копии.

- `tabs` ищется только среди TabNumber/Tab/Tabel. Отсутствие не проверяется: формируется `p.[None]` в основном SQL и запросе фотографий. Подтверждено тестом генерации идентификатора; на такой схеме запрос неработоспособен.
- Связь жёстко задана `m.Owner = p.ID` (с некоторыми альтернативными именами Owner); не проверяются PK/FK и число несопоставленных ключей.
- Запрос начинается с pList LEFT JOIN pMark: ключи без соответствующей записи pList не попадут в выгрузку вообще.
- Метаданные собираются по TABLE_NAME без TABLE_SCHEMA, а запросы используют неквалифицированные таблицы; обнаружение базы дополнительно предполагает dbo. При нескольких схемах возможна неверная диагностика.
- CodeP всегда приводится к VARBINARY(200). Для текстового HEX это будут байты текста, для nvarchar — иная последовательность, для числового типа — другое представление. Для длинных значений возможна обрезка. Нужно определить реальный SQL-тип и сохранить исходное значение/длину, а не считать результат универсальным двоичным кодом карты.

Эти причины условны относительно объекта: необходима схема настоящей базы.

### 6. Теряются идентичность и состояния доступа

`Выгрузка_из_Болид.pyw:308–327, 378–384`; `Миграция_Болид_Sigur.pyw:716–800`.

ID сотрудников и ключей исключаются из штатного экспорта. Группировка сотрудников идёт по табельному номеру/ФИО/отделу, а без табельного — по ФИО/отделу. Две разные записи с одинаковыми ФИО и отделом сливаются; тест подтверждает это поведение. Дубликаты карт и назначение одного номера разным сотрудникам не блокируются.

Status, Schedule/Shedule, Gtype, CodePAdd и другие поля исключены. Постоянство CodePAdd не проверяется. Поэтому выгрузка не является полной архивной копией ключей; нельзя восстановить их исходные состояния и расписания по одному CSV. При выдаче прав в Sigur без дополнительной проверки есть риск активировать заблокированные/неподходящие ключи.

Нужны устойчивые SourcePersonID/SourceKeyID, исходные статусы, типы, полные сроки и отдельное согласование прав. Перенос номера карты не равен переносу права доступа.

### 7. Дополнительные ошибки

- Фото без табельного номера: ключ словаря при выгрузке строится по фамилии+имени, поиск — по фамилии+имени+отчеству (`Выгрузка…:431–459`). Фото с отчеством может остаться не привязанным. Имена файлов также могут совпасть и перезаписаться.
- Срок действия может угадываться по любой похожей дате (`Миграция…:421–456`). Нужна явная привязка и проверка календарной даты; `norm_date` не валидирует её существование.
- После поиска базы сохранённый `auth_ok` имеет приоритет над вновь введённым логином (`Выгрузка…:688`). Изменение полей учётной записи не обязательно меняет фактически используемые данные.
- Подключение собирается конкатенацией без экранирования ODBC-значений. Пароли с разделителями могут ломать строку подключения. Шифрование отключается для новых драйверов; удалённое подключение требует отдельной безопасной настройки.
- Основная выгрузка и перебор серверов выполняются в GUI-потоке; последовательные таймауты могут выглядеть как зависание.
- Экспорт фотографий выполняется до создания CSV; ошибка доступа к фото может сорвать выгрузку ключей целиком. Лучше независимые стадии и атомарная запись результатов.
- XLS имеет ограничения строк/столбцов; проверки размера перед записью нет. Для новой реализации предпочтителен XLSX, если он поддерживается целевой версией Sigur.

## Что проверено запуском

`audit/reproduce.py` выполняет шесть синтетических сценариев, не обращается к SQL и не содержит настоящих карт. `audit/reproduction.txt` — результаты. Зависимости: xlwt, xlrd. Запуск из корня: `python audit/reproduce.py`.

Сценарии: срез W34, принятие невалидных кодов, обрезание 7→5 с чтением записанного XLS, слияние сотрудников, `[None]` в SQL-идентификаторе, отсутствие autocommit в параметрах подключения из копии. Эти тесты подтверждают дефекты/расхождения текущей версии, а не успешность миграции.

## Следующий безопасный этап

1. Уточнить, какая программа и на каком действии падает. Получить точный текст ошибки/лог, версии Орион Про, СУБД и Sigur. До исправления не использовать восстановление .bak на рабочем SQL Server.
2. Получить только метаданные pList/pMark: схема, столбцы, SQL-типы, PK/FK, количества записей и несопоставленных ключей. Не передавать пароли и полную базу без необходимости.
3. Сделать независимую lossless-выгрузку: исходные ID, CodeP, CodePAdd при наличии, тип/длина кода, статус, сроки, связь с владельцем. Никакого декодирования и отбрасывания на этом этапе.
4. Сверить балансы: все исходные ключи = выгруженные + явно перечисленные исключения. Отдельно проверить NULL, пустые коды, сироты, дубликаты, сотрудников без карт.
5. Проверить алгоритм на нескольких контролируемых тестовых картах каждого используемого типа. Подтвердить W26/W34 и режимы обоих считывателей. Примеры номеров передавать только для тестовых/деактивированных карт, без ФИО.
6. Подготовить строгий конвертер: подтверждённый формат, проверка коллизий, запрет молчаливой обрезки, полный реестр ошибок. Права и статусы согласовать отдельно.
7. Проверить малую группу в тестовом Sigur: импорт, совпадение номера при чтении, правильный владелец, отказ для заблокированных карт, сроки. Лишь после этого планировать массовую миграцию и откат.
